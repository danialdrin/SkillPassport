# AI-Powered Student Skill Intelligence Platform

## Frontend Integration Document

This document describes the backend as it is currently implemented. It is intended to be the frontend team's source of truth for API integration, data rendering, user flows, loading states, and error handling.

## 1. What The Backend Does

The backend is a FastAPI application for a student learning and skill-intelligence platform. It provides:

- User registration, login, JWT authentication, and current-user lookup.
- YouTube learning-resource search with pagination.
- Local medium analysis of YouTube resources using transcript and text-quality signals.
- PDF upload and YouTube URL upload.
- Background strong analysis using Groq to extract topics, concepts, relationships, and important sections.
- Material knowledge graphs generated from strong analysis.
- AI-generated summaries, flashcards, and practice quizzes.
- Adaptive generated quizzes with automatic grading.
- Multi-turn AI technical interviews.
- Competency tracking from quiz and interview evidence.
- Student knowledge graphs and digital skill passports.
- Knowledge-gap recommendations based on competency scores and prerequisites.

The backend stores application data in MongoDB and uses Redis for interactive-content caching. Redis falls back to an in-memory cache when the configured Redis server is unavailable.

## 2. Running The Backend

### Local command

From the repository root:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python run.py
```

The API is then available at:

```text
http://localhost:8000
```

Alternative Uvicorn command:

```bash
uvicorn app.main:app --reload
```

### API documentation generated by FastAPI

- Swagger UI: `GET /docs`
- ReDoc: `GET /redoc`
- OpenAPI JSON: `GET /openapi.json`

The OpenAPI document is useful for generating a typed frontend client, but the three interactive endpoints return untyped LLM-generated JSON and need tolerant frontend parsing.

### Required backend dependencies

- MongoDB must be reachable when the application starts. Startup performs a MongoDB ping.
- `GROQ_API_KEY` is required for strong analysis, interactive content, quizzes, and interviews.
- `YOUTUBE_API_KEY` is required for live YouTube search outside development mode.
- Redis is recommended for shared interactive-content caching, although a local in-memory fallback exists.

## 3. Base HTTP Conventions

### JSON headers

For JSON requests:

```http
Content-Type: application/json
```

For protected requests:

```http
Authorization: Bearer <access_token>
```

### Authentication

All endpoints below marked **Protected** require a valid JWT. The token is returned by `POST /auth/login`.

The backend currently creates tokens with an expiry of 1,440 minutes by default. The token response does not include an expiry timestamp, so the frontend should handle a `401` by clearing the session and sending the user to login.

### IDs and dates

- IDs are MongoDB ObjectId strings, for example `64d0f2b8...`.
- Date fields are ISO-8601 datetime strings returned by FastAPI/Pydantic.
- Scores are normally represented as decimal numbers from `0.0` to `1.0` for per-question raw scores, or `0.0` to `100.0` for competency and final quiz scores.

### Standard error shape

FastAPI errors generally have this shape:

```json
{
  "detail": "Human-readable error message"
}
```

Request validation errors use FastAPI's structured `422` response and contain a `detail` array with `loc`, `msg`, and `type` fields.

Common statuses:

| Status | Meaning                                                                                       | Frontend behavior                                   |
| ------ | --------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `200`  | Successful request                                                                            | Render response                                     |
| `201`  | User/resource created                                                                         | Render response and update local state              |
| `400`  | Invalid ID, invalid input, unavailable prerequisite, or service failure converted by a router | Show `detail` and keep the user on the current flow |
| `401`  | Missing, expired, malformed, or invalid JWT                                                   | Clear auth state and redirect to login              |
| `403`  | Authenticated user attempted to access another user's data                                    | Show an access-denied state                         |
| `404`  | Resource, job, analysis, or graph was not found                                               | Show a not-found or stale-data state                |
| `422`  | Pydantic request validation failed                                                            | Highlight invalid form fields                       |
| `503`  | Live YouTube search is unavailable because the API key is missing in non-development mode     | Show search configuration/unavailable state         |

## 5. Authentication API

### `POST /auth/register` - Public

Creates a user.

Request:

```json
{
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "password": "at-least-6-characters"
}
```

Validation:

- `name`: required, 2 to 100 characters.
- `email`: valid email address.
- `password`: at least 6 characters.

Response `201`:

```json
{
  "user_id": "64d0f2b8...",
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "created_at": "2026-09-06T12:00:00Z"
}
```

The password is never returned. Duplicate email returns `400` with `Email already registered`.


```json
{
  "access_token": "<jwt>",
  "token_type": "bearer"
}
```

Invalid email/password returns `401` with `Incorrect email or password`.

Frontend action: store the token in the chosen auth store and send it as `Authorization: Bearer <token>` on protected requests.

## 6. Resource Search And Intake

### `POST /search` - Protected

Searches YouTube and stores each returned candidate as a pending resource owned by the current user.

Request:

```json
{
  "query": "React hooks",
  "page_token": null
}
```

`query` is required and must contain at least one character. `page_token` is optional and comes from a previous response.

Response:

```json
{
  "candidates": [
    {
      "resource_id": "64d0f2b8...",
      "video_id": "abc123",
      "title": "React Hooks Tutorial",
      "channel": "Tech Academy",
      "thumbnail": "https://...",
      "description": "Video description",
      "is_mock": false,
      "medium_analysis": null
    }
  ],
  "next_page_token": "CAUQAA"
}
```

`next_page_token` may be `null`. With a valid live YouTube key, the current implementation requests up to 50 results. In development without a valid key, it returns five mock candidates with `is_mock: true`. In non-development without a key, it returns `503`.

### `POST /search/{resource_id}/analyze-medium` - Protected

Runs local, non-LLM analysis on a YouTube resource selected from search. The resource must belong to the current user.

Path parameter: `resource_id`.

Response: `ResourceResponse`, with the status changed to `medium_analyzed`.

The analysis fields are:

```json
{
  "relevance": 0.0,
  "topic_coverage": 0.0,
  "depth": 0.0,
  "examples": 0.0,
  "clarity": 0.0,
  "structure": 0.0,
  "redundancy": 0.0,
  "overall": 0.0,
  "transcript_available": true
}
```

The values are numeric local quality signals. `transcript_available: false` means captions were unavailable and the analysis falls back to available title/description content with penalties.

Errors: invalid ID `400`; resource not found or not owned by the current user `404`.

### `POST /resources/{resource_id}/select` - Protected

Selects a searched YouTube resource and starts strong analysis in the background.

Path parameter: `resource_id`.

Response `200`:

```json
{
  "resource_id": "64d0f2b8...",
  "status": "selected",
  "job_id": "64d0f2c1...",
  "message": "Resource selected. Strong Analysis job started in background."
}
```

The frontend should immediately begin polling `GET /jobs/{job_id}`.

### `POST /resources/upload` - Protected

Uploads a PDF or submits a YouTube URL. This endpoint uses `multipart/form-data`.

#### PDF upload

Form fields:

- `file`: PDF file.
- `url`: omit for PDF upload.

Example browser request:

```js
const form = new FormData();
form.append("file", pdfFile);
await fetch(`${API_BASE}/resources/upload`, {
  method: "POST",
  headers: { Authorization: `Bearer ${token}` },
  body: form,
});
```

#### YouTube URL upload

Form fields:

- `url`: YouTube URL.
- `file`: omit for URL upload.

If both are supplied, the file branch wins. A missing file and missing URL returns `400`. Non-PDF filenames return `400`.

Response `200`:

```json
{
  "resource_id": "64d0f2b8...",
  "title": "course-notes.pdf",
  "status": "selected",
  "job_id": "64d0f2c1...",
  "message": "Resource uploaded. Strong Analysis started directly (skipping Medium Analysis)."
}
```

PDF text is extracted page by page and stored internally. Uploaded resources skip medium analysis and go straight to strong analysis.

### `GET /resources` - Protected

Lists up to 100 resources owned by the current user, newest first.

Response: array of `ResourceResponse` objects.

```json
[
  {
    "resource_id": "64d0f2b8...",
    "user_id": "64d0f2a0...",
    "source_type": "youtube",
    "url_or_file": "https://www.youtube.com/watch?v=abc123",
    "title": "React Hooks Tutorial",
    "status": "pending",
    "medium_analysis": null,
    "created_at": "2026-09-06T12:00:00Z"
  }
]
```

Possible resource statuses:

| Status            | Meaning                                      |
| ----------------- | -------------------------------------------- |
| `pending`         | Search candidate saved but not selected      |
| `medium_analyzed` | Local YouTube analysis completed             |
| `selected`        | Strong-analysis job created or running       |
| `strong_analyzed` | Strong analysis and material graph completed |

The response intentionally does not include the strong-analysis ID, raw PDF text, PDF pages, or job status. Keep the `job_id` from selection/upload while processing.

## 7. Background Jobs And Strong Analysis

### `GET /jobs/{job_id}` - Protected

Returns the status of a strong-analysis background job owned by the current user.

Response while running:

```json
{
  "job_id": "64d0f2c1...",
  "type": "strong_analysis",
  "status": "queued",
  "result": null,
  "error": null,
  "created_at": "2026-09-06T12:00:00Z"
}
```

Possible statuses:

- `queued`: job has been created but has not started.
- `processing`: analysis is running.
- `done`: analysis and knowledge graph completed.
- `failed`: analysis failed; inspect `error`.

Successful response:

```json
{
  "job_id": "64d0f2c1...",
  "type": "strong_analysis",
  "status": "done",
  "result": {
    "analysis_id": "64d0f300...",
    "resource_id": "64d0f2b8..."
  },
  "error": null,
  "created_at": "2026-09-06T12:00:00Z"
}
```

Failed response has `status: "failed"`, `result: null` in normal operation, and a string `error`.

Frontend recommendation: poll every 1 to 3 seconds while `queued` or `processing`, stop on `done` or `failed`, and retain the `analysis_id` from `result`.

Strong analysis behavior:

- YouTube transcript or PDF text is used as input.
- Input is limited to the first 10,000 characters for the LLM prompt.
- Output is validated against the strong-analysis schema.
- One correction retry may occur after malformed or schema-invalid JSON.
- Concepts are deduplicated by normalized lowercase name.
- A material knowledge graph is built after successful analysis.

### `GET /analyses/{analysis_id}` - Protected

Returns the full strong-analysis record.

Response:

```json
{
  "analysis_id": "64d0f300...",
  "resource_id": "64d0f2b8...",
  "transcript_or_text": "Stored source text or transcript snippet...",
  "version": 1,
  "extracted_data": {
    "topics": [],
    "concepts": [],
    "relationships": [],
    "important_sections": []
  },
  "created_at": "2026-09-06T12:00:00Z"
}
```

The full `extracted_data` schema is documented in Section 9.

## 8. Interactive Study Content

All three endpoints require authentication, a resource with completed strong analysis, Groq configuration, and Redis dependency access. Results are cached for seven days using the analysis ID and version.

### `GET /resources/{resource_id}/summary` - Protected

Typical response:

```json
{
  "title": "Resource Summary",
  "summary_points": ["Important point one", "Important point two"],
  "key_takeaway": "The main takeaway"
}
```

### `GET /resources/{resource_id}/flashcards` - Protected

Typical response:

```json
{
  "flashcards": [
    {
      "front": "What is a closure?",
      "back": "A function together with its lexical environment."
    }
  ]
}
```

The prompt requests five flashcards, but the frontend should render the returned array rather than assume an exact count.

### `GET /resources/{resource_id}/quiz` - Protected

Typical response:

```json
{
  "quiz": [
    {
      "question": "Which statement is correct?",
      "options": ["A", "B", "C", "D"],
      "answer": "A",
      "explanation": "Why A is correct"
    }
  ]
}
```

This is a casual study quiz. It is different from the adaptive exam API and exposes the generated `answer`, so it should not be treated as a graded assessment.

Common errors:

- `400`: invalid resource ID or strong analysis has not completed.
- `404`: resource not found.
- Provider failures may surface as `500` or another generic server error.

Ownership caveat: the current helper looks up the resource and analysis by ID without consistently checking that the resource belongs to the authenticated user. The frontend should only use IDs returned for the current user, and the backend should add ownership checks before production exposure.

## 9. Strong Analysis Data Model

### Topic

```json
{
  "topic": "Main Topic",
  "subtopics": ["Subtopic"],
  "difficulty": "beginner",
  "skills": ["Skill name"],
  "learning_outcomes": ["Outcome"]
}
```

`difficulty` is normally `beginner`, `intermediate`, or `advanced`.

### Concept

```json
{
  "name": "Concept Name",
  "definition": "Clear concise definition",
  "examples": ["Example"],
  "prerequisites": ["Prerequisite concept"],
  "bloom_level": "understand",
  "difficulty": "intermediate",
  "timestamp_or_page": "03:20"
}
```

`timestamp_or_page` may be `null`.

### Relationship

```json
{
  "from": "Source Concept",
  "to": "Target Concept",
  "relation": "prerequisite"
}
```

Supported relationship values are `prerequisite`, `part_of`, and `related_to`. The API model internally exposes the source and target as `from_concept` and `to_concept` when parsed by Pydantic, but serialized analysis data uses the aliases `from` and `to`.

### Important section

```json
{
  "title": "Section title",
  "timestamp_or_page": "Page 4",
  "why_important": "Why this section matters"
}
```

## 10. Material Knowledge Graph

### `GET /knowledge-graph/material/{analysis_id}` - Protected

Returns the graph generated for an analysis.

```json
{
  "analysis_id": "64d0f300...",
  "nodes": [
    {
      "node_id": "64d0f401...",
      "name": "useeffect",
      "display_name": "useEffect",
      "description": "A React hook...",
      "type": "concept",
      "bloom_level": "understand",
      "parent_id": null,
      "prerequisite_ids": []
    }
  ],
  "edges": [
    {
      "edge_id": "64d0f402...",
      "from_node_id": "64d0f401...",
      "to_node_id": "64d0f403...",
      "relation": "prerequisite",
      "material_id": "64d0f300..."
    }
  ]
}
```

Frontend graph rendering:

- Use `nodes` as vertices.
- Match `edges.from_node_id` and `edges.to_node_id` to `nodes.node_id`.
- Use `relation` to label or style links.
- Use `prerequisite_ids` for a node's prerequisite list.
- A graph may have nodes without edges.

The route authenticates the caller but currently does not explicitly verify that the analysis belongs to that caller.

### `GET /knowledge-graph/student/{user_id}` - Protected

Only the JWT owner can request their own graph. A different user returns `403`.

Response:

```json
{
  "user_id": "64d0f2a0...",
  "skills": [
    {
      "node_id": "64d0f401...",
      "display_name": "useEffect",
      "competency_score": 72.5,
      "last_updated": "2026-09-06T12:30:00Z",
      "evidence_event_ids": ["64d0f500..."]
    }
  ]
}
```

Scores are on a `0` to `100` scale. The list can be empty for a new user.

## 11. Adaptive Exam And Interview APIs

### `POST /exams/quiz/start` - Protected

Requires strong analysis for the resource.

Request:

```json
{
  "resource_id": "64d0f2b8..."
}
```

Typical response:

```json
{
  "assessment_id": "64d0f601...",
  "questions": [
    {
      "question_id": "q_1",
      "type": "mcq",
      "prompt": "Which statement is correct?",
      "options": ["A", "B", "C", "D"],
      "node_id": "64d0f401...",
      "target_bloom": "apply"
    }
  ]
}
```

The current service requests three questions. It never returns `correct_answer` to the frontend.

Question types:

- `mcq`: multiple choice; `options` is populated.
- `short_answer`: free text; `options` is normally `null`.
- `code_explain`: free text/code explanation; `options` is normally `null`.

Difficulty is inferred from existing competency: no state or lower scores produce beginner questions, average scores from 50 to 80 produce intermediate questions, and scores above 80 produce advanced questions.

### `POST /exams/quiz/{assessment_id}/submit` - Protected

Request:

```json
{
  "answers": [
    {
      "question_id": "q_1",
      "user_answer": "A"
    },
    {
      "question_id": "q_2",
      "user_answer": "My explanation..."
    }
  ]
}
```

Response:

```json
{
  "attempt_id": "64d0f700...",
  "assessment_id": "64d0f601...",
  "user_id": "64d0f2a0...",
  "score": 83.33,
  "per_question_result": [
    {
      "question_id": "q_1",
      "raw_score": 1.0,
      "feedback": "Correct choice!",
      "node_id": "64d0f401..."
    }
  ],
  "created_at": "2026-09-06T12:35:00Z"
}
```

MCQs are exact/near-exact graded. Short-answer and code-explain questions receive LLM-based partial credit from `0.0` to `1.0`. Missing submitted answers are treated as empty answers. Submitting records competency evidence for each question.

### `POST /exams/interview/start` - Protected

Request:

```json
{
  "resource_id": "64d0f2b8..."
}
```

Response:

```json
{
  "session_id": "64d0f801...",
  "turn_index": 1,
  "question": "Explain the main concept...",
  "evaluation": null,
  "status": "in_progress"
}
```

### `POST /exams/interview/{session_id}/answer` - Protected

Request:

```json
{
  "answer": "The student's explanation..."
}
```

Response while continuing:

```json
{
  "session_id": "64d0f801...",
  "turn_index": 1,
  "question": "The next interview question...",

    "question_id": "turn_1",

```

After the fifth answered turn, the response has `status: "completed"` and `question: null`. There is no separate interview-end endpoint in the current implementation. Each answer creates competency evidence.

## 12. Digital Skill Passport And Gaps

### `GET /passport/{user_id}` - Protected

Only the JWT owner can request this passport.

Response:

```json
{
  "user_id": "64d0f2a0...",
  "nodes": [
    {
      "node_id": "64d0f401...",
      "display_name": "useEffect",
      "description": "A React hook...",
      "bloom_level": "apply",
      "competency_score": 72.5,
      "last_updated": "2026-09-06T12:30:00Z",
      "evidence_event_ids": ["64d0f500..."]
    }
  ],
  "updated_at": "2026-09-06T12:45:00Z"
}
```

`competency_score` is `0` to `100`. `evidence_event_ids` links the score to quiz/interview evidence records internally. The current route sets `updated_at` to the current request time rather than calculating the latest node update, so use each node's `last_updated` for precise UI timestamps.

### `GET /passport/{user_id}/gaps` - Protected

Returns student knowledge gaps where the stored competency score is below `60.0`.

Response:

```json
{
  "user_id": "64d0f2a0...",
  "gaps": [
    {
      "node_id": "64d0f403...",
      "display_name": "Advanced Effects",
      "competency_score": 42.0,
      "recommended_prerequisites": ["React state", "Component lifecycle"]
    }
  ]
}
```

The prerequisite list is derived from graph edges. A new user can receive an empty `gaps` array because only nodes with recorded student state are considered.

## 13. Frontend User Flows

### A. Registration and session bootstrap

1. Submit `POST /auth/register`.
2. Submit `POST /auth/login`.
3. Store `access_token` and attach it to protected requests.
4. Call `GET /auth/me` on app startup to hydrate the user.
5. On `401`, clear the token and redirect to login.

### B. Discover and rank YouTube resources

1. Submit `POST /search` with a query.
2. Render candidate cards using title, channel, thumbnail, description, and `is_mock`.
3. Optionally call `POST /search/{resource_id}/analyze-medium` for a candidate.
4. Render the returned score fields and `transcript_available`.
5. Use `next_page_token` for the next search request.

### C. Select a YouTube resource for deep learning

1. Call `POST /resources/{resource_id}/select`.
2. Store the returned `job_id`.
3. Poll `GET /jobs/{job_id}`.
4. On `done`, read `result.analysis_id` and fetch the analysis and material graph.
5. Refresh `GET /resources` to see `status: "strong_analyzed"`.

### D. Upload a PDF or YouTube URL

1. Submit `POST /resources/upload` as multipart form data.
2. Store `resource_id` and `job_id` from the response.
3. Poll the job exactly as in the selection flow.
4. Do not display medium-analysis controls for uploaded resources because uploads skip that phase.

### E. Study a completed resource

Once strong analysis is complete, the frontend can request in parallel:

- `GET /analyses/{analysis_id}` for topics, concepts, and sections.
- `GET /knowledge-graph/material/{analysis_id}` for graph visualization.
- `GET /resources/{resource_id}/summary`.
- `GET /resources/{resource_id}/flashcards`.
- `GET /resources/{resource_id}/quiz`.

Show a clear loading state for each generated artifact. Provider failures should be retryable.

### F. Take an adaptive quiz

1. Call `POST /exams/quiz/start`.
2. Render each question according to its `type`.
3. Keep answers in frontend state keyed by `question_id`.
4. Submit all answers to `POST /exams/quiz/{assessment_id}/submit`.
5. Render overall score and per-question feedback.
6. Refresh the passport and student graph after submission because competency state may have changed.

### G. Complete an AI interview

1. Call `POST /exams/interview/start`.
2. Render the returned question.
3. Submit the answer to `/exams/interview/{session_id}/answer`.
4. Render evaluation feedback and the next question.
5. Stop when `status` becomes `completed` and `question` is `null`.
6. Refresh passport/knowledge-gap data after completion.

## 14. Internal Data Collections

The frontend does not access MongoDB directly, but these collections explain the API's data relationships:

| Collection           | Purpose                                                                        |
| -------------------- | ------------------------------------------------------------------------------ |
| `users`              | User identity, normalized email, password hash, creation date                  |
| `resources`          | User-owned YouTube/PDF resources, status, medium scores, source metadata       |
| `jobs`               | Background strong-analysis status, result analysis ID, failure message         |
| `analyses`           | Strong-analysis text snippet, extracted topics/concepts/relationships/sections |
| `skill_nodes`        | Deduplicated concept/skill nodes used by material and student graphs           |
| `kg_edges`           | Material graph relationships and prerequisite links                            |
| `student_kg_state`   | Per-user competency score, last update, evidence IDs                           |
| `competency_events`  | Evidence events produced by quizzes and interviews                             |
| `assessments`        | Generated adaptive quiz questions, including private answer keys               |
| `attempts`           | Submitted quiz answers, score, and per-question results                        |
| `interview_sessions` | Durable interview status and complete turn history                             |
| Redis keys           | Cached summary, flashcard, and practice-quiz JSON for seven days               |

| `REDIS_URL`                  | Redis connection                     |

## 16. Current Implementation Caveats

These are important when designing frontend behavior or planning backend hardening:

- Search returns up to 50 live YouTube results, although older planning documents mention 10.
- There is no interview `end` endpoint. Interviews complete automatically after five answers.
- Strong analysis uses the first 10,000 input characters and stores up to a 5,000-character text snippet in the analysis response.
- Interactive response bodies are untyped and generated by an LLM. Validate defensively and handle missing or extra fields.
- The casual interactive quiz includes its answer, while adaptive exam start intentionally omits answer keys.
- Some analysis, material-graph, and interactive-resource routes do not consistently enforce ownership at lookup time. Treat IDs as user-scoped in the frontend and add backend ownership checks before production.
- Some exam and interview failures are converted broadly to `400`, including provider failures.
- Invalid IDs in a few routes can become generic server errors instead of a clean `400`.
- Passport `updated_at` is request-time metadata; use node-level `last_updated` for actual competency freshness.
- Redis fallback is in-memory and process-local. Cache contents can disappear on restart and are not shared across backend instances.
- Startup depends on MongoDB connectivity.
- The current source configuration contains default connection values. Production deployments should replace them with environment-managed secrets and rotate any exposed credentials.
